## เงื่อนไขก่อนเริ่ม

Admin ต้องเปิดร้านทดสอบ, เพิ่ม menu item ที่พร้อมขาย, และตั้งพิกัดร้านในข้อมูลร้านให้ครบ Customer ต้องเข้าสู่หน้า **โปรไฟล์** และกด **ใช้ตำแหน่งปัจจุบัน** เพื่อบันทึกพิกัดจัดส่งก่อนสั่งอาหารถ้าโทรศัพท์ถามสิทธิ์ตำแหน่ง ให้เลือกอนุญาตเฉพาะขณะใช้งานตามที่ต้องการ

ใน Admin ให้เปิด **ตั้งค่า → กติกาค่าส่งและค่าบริการตามประเภทบริการ** ตรวจ Food/Parcel/Errand และกดบันทึกได้ โดยกติกาทดสอบที่ติดตั้งอยู่เป็นค่าเริ่มต้นส่วนกลาง ไม่ได้ฝังอยู่ในแอปลูกค้า

| Category | Expected result |
|---|---|
| Food | แสดงค่าตั้งต้นและแก้ `base_fee`, `included_km`, `per_km_fee`, `zone_multiplier`, `service_fee` ได้ |
| Parcel | มีชุดค่าเฉพาะของ Parcel แยกจาก Food |
| Errand | มีชุดค่าเฉพาะของ Errand แยกจาก Food |
| Settlement | มี GP ร้านค้าแยกจากกติกาค่าส่ง |

## Scenario A — COD: Customer → Merchant → Rider → Customer

1. Customer เปิดร้านทดสอบ, เพิ่มสินค้า 1 รายการ และเปิดตะกร้า
2. Customer ใส่ที่อยู่จัดส่ง เลือก **เงินสดปลายทาง (COD)** แล้วกดยืนยัน
3. ตรวจหน้า **ออร์เดอร์** ของ Customer ว่ามี order ใหม่, ยอด payable ไม่เท่ากับยอดสินค้าเมื่อมีค่าส่ง และ status เป็น **ร้านค้ารับออร์เดอร์**
4. Merchant เข้าหน้า **Orders** ของร้านเดียวกัน ตรวจว่าเห็น order เดียวกัน จากนั้นกดเริ่มเตรียมสินค้า/เปลี่ยนสถานะตามปุ่มที่ระบบให้
5. Rider เปิด **งานจัดส่ง** ตรวจว่า order ปรากฏในส่วน **งานใหม่ที่พร้อมรับ** เมื่อร้านทำให้พร้อมรับแล้ว กด **รับงาน** เพียงครั้งเดียว
6. Rider เปิดงานที่รับไว้และดำเนินสถานะรับสินค้า/กำลังจัดส่ง/ส่งสำเร็จตาม workflow พร้อมแนบหลักฐานหากหน้าจอกำหนด
7. Customer refresh หน้า **ออร์เดอร์** ตรวจ status สุดท้ายตรงกับ Rider และไม่เห็น order ของลูกค้ารายอื่น

> **ผ่าน** เมื่อ order เดียวกันถูกมองเห็นเฉพาะแต่ละบทบาทที่เกี่ยวข้อง, Rider รับงานได้เพียงคนเดียว, และยอด/สถานะไม่ได้ถูกสร้างจากค่า hard-coded ฝั่ง Customer

## Scenario B — QR / Slip: Customer → Admin → Merchant → Rider

1. Customer เพิ่มสินค้าใหม่ เลือก **โอนผ่าน QR / แนบสลิป** และแนบ JPG, PNG หรือ WEBP ที่มีขนาดไม่เกิน 1 MB
2. Customer ยืนยันออร์เดอร์ ตรวจว่า status เป็น **รอตรวจสอบการชำระเงิน** และยังไม่แสดงเป็นงานใหม่ของ Rider
3. Admin เปิดส่วนตรวจชำระเงิน ตรวจ order และหลักฐานการโอน อนุมัติหรือปฏิเสธตามปุ่มที่มี
4. หากอนุมัติ Merchant ต้องเห็น order และสามารถเริ่มเตรียมสินค้าได้ จากนั้นดำเนิน Scenario A ข้อ 5–7
5. หากปฏิเสธ Customer ต้องเห็นสถานะ/ข้อความที่สอดคล้อง และ Merchant/Rider ต้องไม่สามารถดำเนิน order ต่อได้

| Check | Expected result |
|---|---|
| Upload limit | ไฟล์เกิน 1 MB ถูกปฏิเสธจาก storage แม้ client ไม่สามารถบีบอัดได้ |
| Payment review | QR/Slip อยู่ในคิว Admin เท่านั้นก่อนอนุมัติ |
| Expected amount | Admin เห็นยอด payable ที่รวมค่าส่งจาก server ไม่ใช่ยอดสินค้าอย่างเดียว |
| Visibility | Customer อ่านสลิปตนเอง, Admin ตรวจได้, Merchant/Rider ไม่มีสิทธิ์เปิดสลิป |

## Scenario C — Admin media → Customer rendering

1. Admin เปลี่ยนโลโก้/ชื่อแบรนด์ใน Settings หรือเพิ่มสื่อร้าน/โฆษณาจากหน้าที่เกี่ยวข้อง แล้วกดบันทึก
2. เปิด Customer URL ในหน้าต่างไม่ล็อกอินหรือ incognito และ refresh หนึ่งครั้ง
3. ตรวจโลโก้/ชื่อแบรนด์, banner และสื่อร้านที่เกี่ยวข้อง ว่าเปลี่ยนตามข้อมูล Admin โดยไม่มีรูปแตกหรือข้อความ Data URL ปรากฏแทนรูป
4. อัปโหลดรูปที่เกิน 1 MB หนึ่งครั้งเพื่อยืนยันว่าถูกปฏิเสธอย่างชัดเจน จากนั้นอัปโหลด JPG/PNG/WEBP ขนาดไม่เกิน 1 MB เพื่อยืนยันเส้นทางสำเร็จ

> **ผ่าน** เมื่อ Customer อ่าน `brand_public` ได้ก่อน login, catalog media แสดงจาก public bucket และ payment/delivery proofs ยังคง private ตาม role.

## ผลที่ต้องบันทึกเมื่อพบปัญหา

ให้บันทึกเวลาทดสอบ, URL, บทบาทที่ล็อกอิน, ขั้นตอนก่อนเกิดปัญหา, ข้อความ error และภาพหน้าจอ ห้ามแนบข้อมูลบัตร, รหัสผ่าน หรือข้อมูลส่วนบุคคลที่ไม่จำเป็น หาก order ทดสอบมีผลต่อยอดจริง ให้ Admin ยกเลิก/ปิดรายการตาม workflow หลังทดสอบเสร็จ
