# แผนทดสอบ End-to-End: Customer → Merchant → Rider

**ระบบ:** AP Service  
**เวอร์ชันแผน:** 1.0  
**วัตถุประสงค์:** ยืนยันว่าออร์เดอร์หนึ่งรายการเดินทางข้าม 3 application ได้ครบถ้วน ตั้งแต่ลูกค้าสั่งซื้อ ร้านค้าเตรียมสินค้า ไรเดอร์รับและจัดส่ง จนลูกค้าเห็นสถานะสุดท้ายและข้อมูลตรงกันทุกบทบาท

> แผนนี้ใช้สถานะกลางและสิทธิ์การเปลี่ยนสถานะจาก `shared/ap-service-core.js` ของ AP Service ซึ่งเป็นสัญญาร่วมระหว่าง application ทั้งหมด

## 1. ขอบเขตและเกณฑ์สำเร็จ

แผนครอบคลุมคำสั่งซื้อสินค้า/อาหารจากร้านค้าเพียงร้านเดียว โดยทดสอบทั้งเส้นทางปกติ การชำระเงิน และกรณีผิดพลาดที่เสี่ยงทำให้ข้อมูลระหว่าง Customer, Merchant และ Rider ไม่ตรงกัน การทดสอบต้องใช้บัญชีและข้อมูลจริงใน **staging/test data** เท่านั้น ไม่ควรใช้รายการลูกค้าจริงหรือสร้างยอดการเงินจริงโดยไม่มีแผนย้อนกลับ

| ในขอบเขต | นอกขอบเขตของรอบแรก |
|---|---|
| Login และการแยกสิทธิ์ 3 บทบาท | Dispatch algorithm ขั้นสูงและการคำนวณหลาย Rider พร้อมกัน |
| ค้นหาร้าน, เลือกเมนู, ตะกร้า, ที่อยู่และการยืนยันออร์เดอร์ | การชำระเงินจริงกับธนาคาร/ผู้ให้บริการภายนอก |
| QR/สลิปในสถานะรอตรวจสอบ, COD ตามการตั้งค่าปัจจุบัน | Multi-store order และการแบ่งค่าส่งหลายร้าน |
| Merchant เตรียมสินค้า, Rider รับงาน/รับสินค้า/จัดส่ง | การทำ settlement หรือถอนเงินหลังงานจบ |
| สถานะ, notification, refresh, browser back และข้อมูลข้าม application | Load test จำนวนผู้ใช้งานพร้อมกันระดับ production |

ออร์เดอร์จะถือว่า **ผ่าน E2E** เมื่อเลขออร์เดอร์เดียวกัน, ร้านค้า, รายการสินค้า, ยอดเงิน, ที่อยู่, Rider และสถานะล่าสุดตรงกันในทุกหน้าที่มีสิทธิ์เห็นข้อมูลนั้น และการเปลี่ยนสถานะถูกบันทึกเพียงครั้งเดียวตามลำดับที่อนุญาต

## 2. สถานะกลางและสิทธิ์ที่ต้องตรวจ

| ลำดับ | สถานะ | ผู้ที่ทำให้เกิดสถานะได้ | เงื่อนไข E2E ที่ต้องยืนยัน |
|---:|---|---|---|
| 1 | `รอตรวจสอบการชำระเงิน` | Customer | ออร์เดอร์และสลิป/ข้อมูลชำระเงินถูกส่งเข้าคิวโดยไม่เปิดงานให้ร้านก่อนผ่านเงื่อนไข |
| 2 | `ต้องแนบสลิปใหม่` | Admin | ลูกค้าเห็นคำขอแก้ไขและสามารถแนบสลิปใหม่ได้ |
| 3 | `ร้านค้ารับออร์เดอร์` | Admin ตาม payment/review gate | Merchant มองเห็นเฉพาะออร์เดอร์ที่พร้อมปฏิบัติงาน |
| 4 | `กำลังเตรียมสินค้า` | Merchant | Customer และ Rider ที่เกี่ยวข้องเห็นสถานะเดียวกันหลัง refresh |
| 5 | `ไรเดอร์กำลังไปรับ` | Merchant หรือ Rider ตาม transition ที่อนุญาต | งานปรากฏแก่ Rider ที่มีสิทธิ์ และ Merchant เห็นว่า Rider เข้ารับงานแล้ว |
| 6 | `ถึงร้านค้า` | Rider | Merchant เห็น Rider ถึงร้านและลูกค้าเห็นความคืบหน้า |
| 7 | `รับสินค้าแล้ว` | Rider | สถานะงานไม่สามารถย้อนข้ามลำดับได้ |
| 8 | `กำลังไปส่ง` | Rider | แสดงข้อมูลการจัดส่งที่ถูกต้องโดยไม่เปิดข้อมูลส่วนเกินให้บทบาทอื่น |
| 9 | `สำเร็จแล้ว` | Rider | ออร์เดอร์ปิด, ไม่ปรากฏเป็นงานเปิด และประวัติครบถ้วน |
| ทางเลือก | `ยกเลิก` | Customer/บทบาทที่มีสิทธิ์ตามช่วงสถานะ | ไม่มีการสร้างงาน Rider หรือรายการซ้ำหลังยกเลิก |

สถานะ `รอตรวจสอบเครดิต` ให้ทดสอบเพิ่มเมื่อเปิดใช้เครดิตในสภาพแวดล้อมทดสอบ ส่วน `ต้องแนบสลิปใหม่` เป็นเส้นทาง negative test ที่ต้องทดสอบอย่างน้อยหนึ่งครั้งสำหรับการชำระผ่านสลิป

## 5. กรณีทดสอบทางเลือกและกรณีผิดพลาด

| ID | กรณี | ขั้นตอนย่อ | ผลผ่านที่ต้องเห็น |
|---|---|---|---|
| NEG-01 | ไม่ login | Customer กด checkout โดยไม่ login | ระบบพาไป login หรือปฏิเสธอย่างชัดเจน; ไม่สร้างออร์เดอร์ |
| NEG-02 | ข้อมูล checkout ไม่ครบ | ลบเบอร์/จุดส่ง แล้วกดยืนยัน | Validation ระบุ field ที่ขาด, ไม่มี order ID ใหม่ |
| NEG-03 | สลิปไม่ผ่าน | ส่งสลิปทดสอบให้ถูกปฏิเสธ/ทำสถานะ `ต้องแนบสลิปใหม่` | Merchant และ Rider ยังไม่เห็นงานเปิด; Customer แนบใหม่ได้ |
| NEG-04 | เปลี่ยนสถานะข้ามขั้น | Rider พยายามปิดงานก่อน `รับสินค้าแล้ว` หรือ Merchant พยายามทำ action นอกสิทธิ์ | Server/UI ปฏิเสธและไม่เปลี่ยนสถานะใน database |
| NEG-05 | กดซ้ำ/เครือข่ายช้า | กดยืนยันออร์เดอร์, รับงาน, หรือเปลี่ยนสถานะซ้ำขณะ loading | มี record/event เดียว, loading state ไม่ทำให้ผู้ใช้กดซ้ำ |
| NEG-06 | ข้ามสิทธิ์ด้วย URL | เปิด URL Merchant/Rider โดยใช้ session Customer หรือเปิด order ของร้านอื่น | RLS/API ปฏิเสธหรือไม่คืนข้อมูลที่ไม่เกี่ยวข้อง |
| NEG-07 | ยกเลิกก่อนร้านเตรียม | Customer ยกเลิกในช่วงที่ policy อนุญาต | ทุกบทบาทเห็น `ยกเลิก`, Rider ไม่มีงาน active และรายการไม่กลับมา |
| NEG-08 | Refresh/Back ระหว่างทำงาน | Refresh หรือกด Back หลัง Rider รับงาน แล้วกลับเข้าหน้าเดิม | สถานะล่าสุดจาก server ถูกโหลดกลับมา ไม่สร้าง action ซ้ำหรือหน้า blank |
| NEG-09 | แจ้งเตือนและ polling | Merchant/Rider ปล่อยหน้าไว้, Customer สร้างออร์เดอร์ใหม่ | Badge/notification refresh แบบไม่ block navigation และข้อมูลใหม่ปรากฏภายในรอบ sync ที่กำหนด |
| NEG-10 | ความสอดคล้องยอดเงิน | เปรียบเทียบยอดสินค้า, ส่วนลด, ค่าส่ง และยอดสุทธิ 3 ฝั่ง | ใช้ข้อมูล order เดียวกัน ไม่มี client-side override หรือค่าการเงิน hardcode |

## 8. เกณฑ์ออกจากรอบทดสอบ (Exit Criteria)

รอบนี้ผ่านเมื่อ Happy Path E2E-01 ถึง E2E-13 ผ่านทั้งหมด, negative tests ที่เกี่ยวกับสิทธิ์/การเงิน/การสร้างออร์เดอร์ซ้ำผ่านทั้งหมด, ไม่มี defect ระดับ Blocker หรือ Critical ค้างอยู่ และไม่พบความต่างของเลขออร์เดอร์หรือสถานะระหว่าง 3 application

| ระดับข้อผิดพลาด | ตัวอย่าง | เงื่อนไขก่อนอนุมัติใช้งาน |
|---|---|---|
| Blocker | สั่งซื้อไม่ได้, Rider รับงานไม่ได้, ข้อมูลข้าม role ไม่โหลด | ต้องแก้และทดสอบซ้ำ |
| Critical | ยอดเงินไม่ตรง, ผู้ใช้เห็นข้อมูล order ร้านอื่น, สถานะข้ามขั้นได้ | ต้องแก้และทำ regression ทุกบทบาท |
| Major | notification ไม่มา, refresh แล้วสถานะล่าช้าผิดปกติ, Back แล้วค้าง | ต้องมี fix หรือแผนแก้พร้อม owner/กำหนดเวลา |
| Minor | ข้อความ, spacing, label หรือ loading feedback ไม่ครบ | บันทึกเป็น backlog ได้หากไม่กระทบความถูกต้องของ order |

## 9. ลำดับการใช้งานในวันทดสอบ

เริ่มจาก E2E-01 ถึง E2E-13 ด้วยเส้นทางชำระเงินหลักหนึ่งเส้นทางก่อน เมื่อผ่านแล้วให้ทำ NEG-01 ถึง NEG-10 จากนั้นทำ Happy Path ซ้ำอีกหนึ่งรอบด้วยช่องทางชำระเงินทางเลือก หากมีการแก้ defect ระหว่างวัน ให้ rerun ตั้งแต่ test case ที่สร้าง order จนถึง E2E-13 เสมอ ไม่ควรตรวจเฉพาะหน้าที่แก้ไข เพราะความเสี่ยงหลักของระบบอยู่ที่ข้อมูลและสถานะข้าม application

เมื่อดำเนินการจริง ให้รายงานด้วยตารางสรุป `Test ID | Pass/Fail | Order ID | หลักฐาน | Defect ID | ผู้ตรวจ | เวลา` เพื่อให้ตรวจย้อนหลังและอนุมัติการเปิดใช้งานได้ชัดเจน
